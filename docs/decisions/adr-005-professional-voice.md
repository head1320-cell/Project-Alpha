# ADR 005 — 화면 문체를 전문 용어로 (해요체·쉬운 말을 걷는다)

- 상태: 채택 (2026-11-11)
- 결정한 사람: 사용자 지시("쉬운 단어와 말을 쓰려다 보니 너무 이상하고 어색해졌다. 금융 전문용어를 써도 되니 단어를 다시 전문적으로,
  플랫폼 사용자 관점에서 다 바꿔 달라", 2026-11-11) + 그 뒤 AskUserQuestion 답 셋(아래 §2).
- 정정하는 기록: [ADR 003](adr-003-toss-visual-language-app-wide.md)의 **문체 부분만**. 배치·색·부품(토스식 시각 언어)은 그대로다.
- 용어집: [`docs/specs/2026-11-11-ui-terminology.md`](../specs/2026-11-11-ui-terminology.md)

## 1. 무엇이 문제였나

ADR 003 은 캔버스 밖 탭까지 "토스식"으로 옮기면서 문체도 같이 정했다 — 해요체, 쉬운 말, 영어 낱말 금지.
그 결과 금융 플랫폼의 화면이 이렇게 됐다(2026-11-11 실측 — 프론트 소스의 보이는 문구 7,148개 가운데 해요체 말끝 1,688곳 · 합니다체 45곳):

| 화면에 적힌 것 | 사용자가 기대하는 말 |
|---|---|
| 돈 버는 힘 | 수익성 |
| 우리 추정 내재가치보다 75% 높게 거래돼요 | 괴리율 +75% (고평가) |
| 부도 위험 점수 · 이익 조작 점검 | Altman Z-Score · Beneish M-Score |
| 가장 크게 빠진 폭 | 최대낙폭(MDD) |
| 몰라요 · 재지 못했어요 | N/A · 측정 불가 |

E2E 는 `Z-Score`·`M-Score`·`CAGR`·`MDD`·`Goldilocks` 같은 낱말이 화면에 나오면 실패하게 막고 있었다. 전문 용어를 쉬운 말로 풀다 보니
같은 개념이 화면마다 다른 말로 불렸고, 사용자(투자 리서치·운용을 하는 사람)가 아는 낱말과 화면의 낱말이 어긋났다.

## 2. 결정

1. **문체 = 개조식 + 합니다체.** 라벨·제목·칩·표 머리·단추는 명사형으로 짧게 쓴다. 설명·안내·사유 문장은 합니다체 평서문으로 쓴다.
   해요체(~어요·~예요·~세요)는 쓰지 않는다.
2. **용어 = 국문 전문용어 + 통용 영문 약어.** 업계에서 약어로 통하는 것(PER·ROE·DCF·MDD·CAGR·VaR …)은 그대로 쓴다. 허용 목록은 용어집 §5 에 둔다.
   풀어 쓴 영어 낱말(Overview·Valuation·Peers …)과 개발자 낱말(mock·snake_case 키·예외 이름·환경변수 이름)은 계속 쓰지 않는다.
3. **범위 = 전 화면 + 서버가 화면으로 보내는 문장.**
   - ★2026-11-11 보탬 — 옮기는 방법★ 처음에는 모듈 단위로 옮기려 했다. 재 보니 E2E 단언 745곳 가운데 약 300곳이 서버가 보낸 문장이거나
     여러 모듈에 걸친 문장이라, 한 모듈만 옮기면 단언과 화면이 어긋난다. 그래서 ★말끝과 상태 문구는 변환기 하나로 전 영역(프론트 소스 · E2E ·
     서버 문자열 · pytest)을 한 번에 옮겼다★ — 같은 규칙을 양쪽에 걸어야 어긋나지 않는다. 낱말(용어집 §3)은 그 뒤에 글자 치환과 화면별 손질로 옮긴다.

## 3. 무엇을 유지하나 (바꾸지 않는다)

1. **금지 표현 여섯** — 검증됨·입증됨·견고함·프로덕션 레디·투자 우위·더 나은 전략(CLAUDE.md §2 · `tests/test_frontend_claim_words.py`). 문체가 전문적이 된다고 주장이 세져서는 안 된다.
2. **증거 등급 어휘** — 관측·측정·추론·가정·미상·미검증·합성·실데이터·시점고정·표본외. 저장소가 이미 쓰는 어휘라 새로 만들지 않는다.
3. **미상 ≠ 0.** 모르는 값은 0 이나 빈칸으로 그리지 않고, 사유를 함께 적는다. 낱말만 "몰라요" → `N/A` 로 바뀐다.
4. **답 문장 = 서버 값**(ADR 003 §2.6). 화면은 서버 필드를 정해진 틀에 끼울 뿐 판단을 만들지 않는다. 틀의 말투만 바뀐다.
5. **툴팁 금지 · 고정폭은 식별자에만 · 보이는 em-dash 금지**(화면별 기존 검사) · **CSS 클래스는 E2E 계약** · 요청 골든(서버에 가는 요청은 바이트 그대로).
6. 코드 주석과 문서(HISTORY·스펙)의 말투는 이 결정의 대상이 아니다.

## 4. 어떻게 지키나

- **래칫** `tests/test_frontend_voice.py` — `frontend/src` 의 주석 밖 글자에서 해요체 말끝을 찾는다. 옮긴 폴더는 0건이어야 하고, 아직 옮기지 않은 폴더는
  목록(`PENDING`)에 적는다. 목록의 폴더가 이미 깨끗하면 그것도 실패다(낡은 예외를 남기지 않는다). 목록은 단계마다 줄고 마지막에 빈다 —
  ★어디까지 옮겼는지는 이 목록이 말한다★.
- **화면 검사** `frontend/e2e/helpers.ts::voiceAudit` — 보이는 글자의 해요체·em-dash·툴팁·금지 영어를 한 곳에서 잰다. 스펙마다 흩어져 있던 금지 목록을 이것으로 모은다.
- 문구를 단언하는 스펙은 문구를 바꾸는 **같은 커밋**에서 고친다(ADR 003 §2.1).

## 5. 결과

- 장점: 화면의 낱말이 사용자가 아는 낱말과 같아진다. 같은 개념은 용어집의 한 낱말로 불린다. 라벨이 짧아져 표와 칩이 촘촘해진다.
- 비용: 보이는 문구 약 7,000개와 문구 단언 약 1,350줄을 옮긴다. 옮기는 동안에는 옮긴 모듈(합니다체)과 아직인 모듈(해요체)이 함께 보인다 — 모듈 단위 전환의 대가다.
- 전문 용어는 처음 쓰는 사람에게 어렵다. 풀이는 툴팁이 아니라 보이는 줄(용어 옆 괄호 · 절 머리글)에 둔다 — 예: `MDD(최대낙폭)`.
