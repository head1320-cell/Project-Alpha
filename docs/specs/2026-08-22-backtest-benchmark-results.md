## 1. ★정합성 — 가설이 아니라 사실이 됐다★

`_generate_signal_as_of()`(`src/kis_backtest_engine.py:675`)는 모듈 전역
`src.kis_data_fetcher.get_daily_prices` / `get_current_price` 를 패치하고 `finally`
에서 되돌린다. 되돌릴 값은 **진입 시점의 전역**이다(`:677`) — 이미 다른 스레드가
패치해 뒀다면 **그 람다를 "원본" 으로 저장**한다.

서로 겹치지 않는 종목 집합으로 **동시 실행 2개**를 돌린 결과:

| 측정 | 값 |
|---|---|
| 동시 실행 | 2 |
| 벽시계 | 9.16s |
| 전역 샘플 | 4,149 |
| **패치된 상태로 관측된 샘플** | **3,978 (95.9%)** |
| 공유 전역에서 관측된 서로 다른 티커 | **42** |
| **자기 데이터가 공유 전역에 올라온 실행 수** | **2 / 2** |
| **두 실행이 끝난 뒤에도 전역이 오염됨** | **`true`** |
| `get_daily_prices` 누수 | `true` |
| `get_current_price` 누수 | `true` |
| 엔진 오류 | **없음 (`[]`)** |

**읽는 법 셋:**

1. **오염이 영구적이다.** 두 실행이 다 끝난 뒤에도 전역이 원본이 아니다. 이후 그
   프로세스의 **모든** 백테스트와 **모든 현재가 조회**가 완료된 실행의 얼어붙은
   DataFrame 을 받는다. `uvicorn --workers 1` 이므로 프로세스는 하나뿐이다.
2. **창이 좁지 않다.** 동시 실행 중 전역은 96% 의 시간 동안 패치 상태다.
   드물게 터지는 경쟁이 아니라 사실상 상시다.
3. **★조용하다★** 두 실행 모두 **오류 없이 결과를 반환했다.** 화면·DB·재현 좌표
   어디에도 "이 결과는 다른 실행의 데이터를 읽었을 수 있다" 는 신호가 없다.

프롬프트가 "반드시 보존" 하라고 한 목록의 첫 항목이 **결정론·재현성**이다.
동시 실행에서 그 계약은 지금 지켜지지 않는다.

## 3. ★GIL — 스레드가 처리량을 전혀 못 산다★

동일 작업(20종목 × 1년)을 동시 N개. **CPU 4개인 기계다.**

| 동시 실행 | 벽시계 | CPU 시간 | **CPU 사용률** | 실행당 | 최대 스레드 |
|---|---|---|---|---|---|
| 1 | 4.15s | 4.45s | **107.2%** | 4.15s | 9 |
| 2 | 10.23s | 10.57s | **103.4%** | 5.11s | 16 |
| 4 | **27.06s** | 28.53s | **105.4%** | 6.76s | 24 |

**읽는 법 둘:**

1. **CPU 사용률이 동시성과 무관하게 ~105% 다.** 스레드가 확장된다면 4개일 때
   ~400% 여야 한다. 코어 하나에 묶여 있다 — **GIL 이 천장**이고, 남은 코어 3개는 논다.
2. **★동시 실행이 순차 실행보다 느리다★** 4개 동시 = 27.06s vs 순차 4×4.15 = **16.6s**.
   **63% 손해**다. 지금의 스레드 모델은 단순 순차 큐보다 **엄격히 나쁘다** —
   처리량은 하나도 못 사고 지연(4.15→6.76, +63%)과 스레드 수(9→24)만 늘린다.

이것이 **프로세스 격리(안 A)** 를 고르는 정량적 근거다. 같은 4코어에서 프로세스
4개는 ~4배를 준다. 스레드 4개는 0.61배를 준다.

| 규모 | 종목×거래일 | 벽시계 | **종목·일당** |

로딩은 계속 **2.3%** 다(단, SQLite/mock — §환경).

### 규모 확장 — 종목·일수의 곱에 선형, 그리고 시뮬 비중이 **커진다**

| 규모 | 종목×거래일 | 벽시계 | 종목·일당 | **simulating 비중** | RSS |
|---|---|---|---|---|---|
| small | 5,200 | 17.2s | 3.30 ms | 91.6% | 90 MB |
| medium | 78,100 | 182s | 2.33 ms | 96.5% | 121 MB |
| **large** | **479,975** | **1152s** | **2.40 ms** | **97.5%** | **247 MB** |

읽는 법 셋:

1. **숨은 2차 항이 없다.** 종목·일당 비용이 3.30 → 2.33 → 2.40 ms 로
   수렴한다. 비용은 **종목·일 단위 파이썬 작업**에 그대로 비례한다.
2. **규모가 커질수록 시뮬 비중이 커진다** (91.6% → 96.5% → 97.5%).
   로딩 최적화의 상한이 그만큼 낮다 — large 에서 로딩을 **0초로 만들어도 2.2% 절약**이다.
3. **메모리가 실행당 247 MB 다.** 동시성 상한이 없으므로 곱해진다 —
   실행 8개면 ~1.9 GB. 상한이 필요한 두 번째 이유다.

### ★외삽 — 전 유니버스 백테스트★

`universe_eval_cap` 상한은 **4,000** 이고 10년은 ~2,470 거래일이다.
2.40 ms/종목·일을 그대로 적용하면 **6.6 시간** — 단일 스레드로.
그리고 GIL 때문에 동시 실행은 이것을 **더 느리게** 만든다(§3).
외삽이므로 실측이 아니라는 것을 명시한다.

## 5. 이 실측이 **반증한** 것

프롬프트의 가설은 "CPU 경합 · DB 경합 · GIL · 메모리 압박 · API 기아" 였다.
전부 맞은 것이 아니다:

| 가설 | 판정 |
|---|---|
| GIL 제약 | **확인** — §3, CPU 사용률 105% 고정 |
| CPU 경합 | **확인** — 동시 실행이 순차보다 63% 느림 |
| DB 경합 | **이 형상에서는 미확인** — 로딩이 전체의 1.8%. 단 SQLite/mock 이라 Postgres 에서는 다시 재야 한다(§환경) |
| 메모리 압박 | **경미** — 실행당 RSS +90 MB, 피크 36 MB. 상한 없는 동시성과 곱해지면 문제지만 단일 실행은 여유 |
| API 기아 | **간접 확인** — 워커가 API 프로세스와 같은 GIL 을 점유. 별도 측정 필요 |

그리고 프롬프트가 **예상하지 않은** 것이 하나 나왔다 — §1 의 정합성 결함이고,
그것이 성능보다 먼저 다뤄야 할 문제다.
