# AT · 업무 응답이 breaker 를 여는가를 잰다 — ★링은 카운터와 같은 수명을 산다★

작성 2026-09-21 · 구현 `src/domain/failure_streak.py` ·
`kis_client.CircuitBreaker` · `api_health` · `api_failure_probe` ·
`kill_switch.should_auto_trigger` · 선행 AR·AS · 기록 `docs/HISTORY.md` 의 AT 항목

## 1. 왜

AR 이 드러낸 안전 역전이 아직 살아 있다: `_request` 가 `rt_cd != "0"` 에서도
`record_failure()` 를 부르므로 ★장 종료·잔고 부족 같은 정상 업무 응답이 KIS
장애와 같은 카운터에 들어간다★. 연속 5회면 breaker 가 `OPEN` 이 되고,
AQ 가 통로를 이었으므로 `auto_api` 가 *"KIS API 연속 실패 (5회)"* 로 킬스위치를
겨냥한다. 5회가 전부 업무 응답이었다면 **틀린 진단**이다.

AS 가 코드 목록을 낼 수 있게 했지만 ★아직 아무도 그 숫자를 보지 않는다★ —
판정이 내려지는 자리에서는 그 5회의 구성을 알 수 없다.

## 2. ★실측 — 구성은 기존 기록으로 재구성할 수 없다★

| 실측 | 결과 |
|---|---|
| `record_failure()` 의 인자 | ★없다★ — breaker 가 눈먼 채로 센다 |
| 기록되는 종류 | `last_failure_kind` ★한 칸★뿐 |
| `_request` 호출부 | 7곳(잔고·시세·분봉·투자자·주문·취소 등) |
| 그중 감사 행이 남는 것 | ★둘★(주문·취소)뿐 |
| `failure_count` 가 0 이 되는 자리 | ★둘★ — `record_success` · `call_allowed` 의 HALF_OPEN |
| `"KIS API 연속 실패 (N회)"` 부분문자열 계약 | ★0건★(테스트는 `out[0] == "auto_api"` 로 source 만 건다) |

`get_balance` 실패 5회로 breaker 가 열려도 AS4 의 원장은 **아무것도 모른다**.
그래서 ★숫자와 같은 객체에 같은 수명으로★ 기록한다.

## 3. 어떤 질문에 답하는가

CLAUDE.md §2 의 네 질문 중 어느 것도 아니다 — 예측력도 경제적 가치도 재지
않는다. 재는 것은 ★발동 근거의 품질★ 하나다: *"이 발동을 만든 5회가 무엇이었나."*

산출은 **동작 변경의 근거가 될 수치**이고, 동작 변경 자체는 별도 승인 사항이다.

## 4. 왜 메모리 링인가

breaker 자체가 프로세스 로컬 메모리 상태이고, CLAUDE.md 가 `uvicorn --workers 1`
을 박은 이유가 *"캐시·쿼터·적재 상태가 프로세스 로컬"* 이다. ★구성이 그 숫자를
설명하려면 같은 수명을 살아야 한다.★

감사 로그에 KIS 실패를 전부 쓰는 안은 영속적이지만 ★실거래 호출 경로에 DB
쓰기를 새로 넣는다★ — 시세 조회는 빈번하고, 쓰기가 느리거나 실패할 때 무슨
일이 일어나는지가 새 문제로 생긴다. 둘 다 두는 안은 ★같은 사실이 두 곳에
있게 되어 어긋날 때 무엇이 진실인지 정하는 문제★를 만든다(AS 가 새 카운터를
거부한 바로 그 이유).

## 5. ★핵심 계약 — 두 자리 모두★

```
record_success()             → 성공했으니 연속이 끊겼다     → 링도 비운다
call_allowed() 의 HALF_OPEN  → 시간이 지나 다시 열어 본다   → 링도 비운다
```

★하나만 비우면 구성이 **다른 집합**을 설명하게 된다.★ 그리고 링이 넘치거나
누가 `failure_count` 를 직접 건드렸을 수 있으므로, 개수가 어긋나면
`describes_count: False` 로 ★비율을 말하지 않는다★ — 조용히 내면
*"5회 중 3회가 업무 응답"* 이라는 틀린 비율이 만들어진다.

## 6. 구성 요소

### 6.1 `src/domain/failure_streak.py` ★NEW★ (순수)

`streak_composition(kinds, *, count=None)` → `n_recorded` · `count` · `by_kind`
· `labels` · `dominant` · `business_n` · `all_business` · `counted_n` ·
`describes_count` · `reason` · `note`.

★빈 것에 전칭을 주장하지 않는다★ — 파이썬에서 `all([])` 은 `True` 라, 0회 중
0회가 업무 응답인 것이 "전부 업무 응답" 으로 읽힌다(아무 일도 없는 상태가
가장 강한 주장이 된다).

`streak_phrase(composition)` → 판정 사유 옆에 붙는 한 문장. ★비어 있는 법이
없다★. 설명하지 못하면 비율 대신 그 사실을 말한다.

★책임 소재를 말하지 않는다★ — `business` 의 뜻은 여전히 미상이다(AS 의 표가
비어 있다). 그래서 이 모듈은 `kis_rt_cd` 를 임포트하지 않는다(AST 테스트).

### 6.2 `CircuitBreaker` — 경계 있는 링

`record_failure(kind=None)`. ★기본값이 관측 행세를 하지 않게★ 모르면
`unknown` 이고, 어휘 밖의 값도 마찬가지다. `streak_kinds()` 는 스냅샷을 준다.
`STREAK_RING = 20`(임계 5보다 넉넉하게 — 임계만큼만 담으면 넘치는 순간 구성이
사실상 언제나 카운트와 어긋난다).

★세는 것은 0줄 바뀌지 않았다★ — 임계값도, 어떤 종류가 카운트되는지도 그대로다.

### 6.3 관측이 구성을 싣는다

`api_failure_observation(..., streak=...)` 가 ★숫자에 건 규칙을 구성에도
건다★: `broker` 출처가 아니면 구성도 내지 않는다(`MockKISClient` 에는 breaker
가 없으므로 그쪽의 구성은 합성이다).

★접는 일은 `api_health` 가 하지 않는다★ — 그 모듈은 `src` 안의 무엇도
임포트하지 않는 잎이고, 그 경계를 지키는 가드가 이미 있다. 부르는 쪽
(`api_failure_probe`)이 접어서 넘긴다.

### 6.4 판정 자리

`should_auto_trigger` 의 `auto_api` 사유가 구성을 데리고 간다:

    KIS API 연속 실패 (5회 — 5회가 전부 업무 응답(rt_cd 미검증), 뜻은 미상: …)

이 문자열은 `live_kill_events` 에 ★그대로 저장★되므로 사건 조사를 하러 그
행을 열었을 때 구성이 남아 있다 — **DDL 변경 0줄**. `/kill-switch/readiness`
는 `api_failure_observation` 을 그대로 내보내므로 구성이 함께 실린다.

★판정 조건은 한 글자도 바뀌지 않았다★ — 5회가 전부 업무 응답이어도 여전히
발동한다. 프런트는 **타입만**.

## 7. 오류 처리

| 상황 | 결과 |
|---|---|
| 종류가 어휘 밖 | `unknown` — ★버리지도 믿지도 않는다★ |
| 링이 없는 옛 객체 | 구성 없음 — ★없으면 지어내지 않는다★ |
| 링이 넘침 | `describes_count: False` + 사유 |
| 센 횟수 미상 | `describes_count: None` — ★미상 ≠ 일치★ |
| 관측 블록 없음 | 사유는 예전 모양 그대로 — ★관측이 판정의 조건이 아니다★ |

## 8. ★이 설계가 하지 않는 것★

- **breaker 가 무엇을 세는지 바꾸지 않는다.** 업무 응답은 **여전히** 카운트에
  들어가고 여전히 발동시킨다 — 이제 그 사실이 발동 기록에 **남을** 뿐이다.
  ★재는 것과 막는 것은 다르다.★
- **임계값을 바꾸지 않는다.**
- **책임 소재를 말하지 않는다.** AS 의 표가 비어 있다.
- **감사 로그에 KIS 실패를 새로 쓰지 않는다.** 실거래 호출 경로에 DB 쓰기를
  넣지 않는다.
- **재시도·백오프를 만들지 않는다.**
- **채점표 #12 를 올리지 않는다.**
- **화면을 만들지 않는다.** 타입까지다.
