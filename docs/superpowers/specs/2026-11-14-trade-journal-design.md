# 매매일지 v1 — 체결 내역을 넣으면 어디서 벌고 어디서 새는지 (설계 · 2026-11-14)

> 근거: [ADR 006](../../decisions/adr-006-trader-tool-scope.md) §2-7 · [로드맵](../../plans/2026-11-14-pb-trader-tool-roadmap.md) 3단계에서 앞으로 당긴 묶음 · 승인된 계획(W3).
> 고객군: ★전업투자자 · 헤비 트레이더★ — 이미 매매하고 있는 사람. 첫 물음은 "내 매매의 어디서 돈이 새나"다.
> 이 도구가 답하는 질문은 ★"무엇이 일어났는가"★ 하나다(관측). "앞으로 어떻게 될 것인가"·"무엇을 사야 하는가"에는 답하지 않는다.

## 1. 왜 이것부터인가

- 증권사 API · 시세 계약 · 회사 승인 없이 ★자기 체결 내역 파일만으로★ 된다.
- 종목을 고르거나 권하지 않는다 — [도구 제공의 경계](../../specs/2026-11-14-tool-provision-boundary.md)의 조건을 구조로 채운다(C1 종목·조건은 고객이 정한다 · C6 고객 정보는 고객 쪽 · C7 비용 먼저 · C8 결과에 등급).
- 설계 원칙 "고객이 오래 살아남게"에 바로 닿는다 — 비용이 이익의 몇 할을 가져가는지, 지금 손익비에서 몇 할을 이겨야 본전인지를 숫자로 보여 준다.
- 뒤 단계(백테스트 ↔ 실거래의 괴리)의 기준선이 된다.

## 2. 이름과 자리 (계획에서 고친 것 하나)

계획은 화면 `/journal` · 라우트 `/api/v1/journal/analyze` 였다. 저장소에 이미 ★다른 일지★가 있다 — 리서치 의사결정 일지(`/api/v1/allocation/journal` · `src/data/journal_store.py`).
섞이지 않게 이름을 가른다: 화면 **`/trade-journal`** · 라우트 **`POST /api/v1/trade-journal/analyze`** · 엔진 **`src/engine/trade_journal/`** · 화면 이름 **매매일지**.

## 3. 흐름

```
[브라우저]  파일 고르기 → 글자 풀기(UTF-8 · EUC-KR) → 표로 읽기 → 열 맞추기 → 미리 보기 → 설정(수수료 · 모르는 종목의 시장)
     │  정규화한 줄만 보낸다(파일 원문은 보내지 않는다)
     ▼
[서버]  POST /api/v1/trade-journal/analyze — 로그인 필요 · 줄 수 상한 · ★저장하지 않는다★
     │  줄 검사 → 왕복 매칭 → 비용 → 지표
     ▼
[브라우저]  결과: 요약 띠 · 누적 실현 손익과 고점 대비 하락 · 비용 분해 · 시간대·요일 · 보유 시간 · 종목 표 · 거래 표 · 버린 줄과 사유
```

## 4. 입력

### 4.1 파일

- 쉼표·탭으로 가른 글 파일(.csv · .txt). 엑셀 파일(.xlsx)은 v1 에서 받지 않는다(안내 문장으로 "CSV 로 저장").
- 글자: UTF-8 로 풀어 보고 깨지면 EUC-KR(국내 HTS 내보내기의 흔한 꼴). 브라우저의 `TextDecoder` 로 한다.
- 숫자의 쉼표·원 기호·공백은 걷는다. 괄호나 `-` 접미로 음수를 적는 꼴은 v1 에서 읽지 않는다(그 줄은 사유와 함께 버린다).
- 증권사별 사전 설정은 ★실제 양식을 본 것만★ 둔다 — 지금은 0개다(범용 열 맞추기). 열 이름으로 어림해 미리 골라 주되(예: `체결일시`·`종목코드`·`매매구분`), 사용자가 고친다.

### 4.2 정규화한 한 줄(서버가 받는 모양)

| 칸 | 필수 | 뜻 |
|---|---|---|
| `executed_at` | ✓ | 체결 일시(`YYYY-MM-DD HH:MM[:SS]`). 날짜만 있으면 시각 미상 — 받되 '시간대·보유 시간' 통계에서 뺀다 |
| `symbol` | ✓ | 종목 코드(또는 이름 — 그대로 묶음의 열쇠로 쓴다) |
| `side` | ✓ | `buy` · `sell`(화면이 매수/매도·B/S·1/2 등을 사용자가 고른 대응으로 옮긴다) |
| `quantity` | ✓ | 수량(양수) |
| `price` | ✓ | 체결 단가(양수) |
| `fee` | | 그 체결의 수수료(원). 있으면 ★관측★ |
| `tax` | | 그 체결의 세금(원). 있으면 ★관측★ |
| `market` | | `KOSPI`·`KOSDAQ`·`KONEX` |
| `instrument` | | `stock`·`etf` |
| `name` | | 종목 이름(표시용) |

줄마다 검사한다 — 통과 못 한 줄은 ★사유와 함께 따로 돌려준다★(조용히 버리지 않는다): 읽을 수 없는 일시 · 수량·단가가 양수가 아님 · 매수/매도를 알 수 없음 · 종목 없음.

## 5. 엔진 (`src/engine/trade_journal/` — 순수 함수 · 입출력 없음)

| 파일 | 하는 일 |
|---|---|
| `fills.py` | 줄 검사 · 정규화(`normalize`) — 통과한 체결과 버린 줄(줄 번호 · 사유) |
| `matching.py` | 왕복 매칭(`match`) — 종목별 선입선출 · 부분 체결 · 미청산 |
| `costs.py` | 체결마다 수수료·세금과 그 ★근거★(관측 · 추론 · 가정 · 미상) |
| `metrics.py` | 지표(`summarize` 등) |
| `__init__.py` | `analyze(rows, options)` — 위 넷을 잇는 한 함수 |

### 5.1 왕복 매칭

- **단위는 둘이다.** ⑴ 묶음 맞추기 — 매도 수량을 그 종목의 가장 오래된 매수 수량부터 맞춘다(선입선출). 손익·보유 시간은 여기서 나온다.
  ⑵ **거래(왕복)** — 한 종목의 보유 수량이 0 에서 시작해 다시 0 이 될 때까지를 한 번으로 센다. 나눠 사고 나눠 팔아도 한 번이다(단타 매매의 감각과 맞는다). 승률·손익비·연속 손실은 이 단위로 센다.
- 파일이 끝났는데 0 으로 돌아오지 않은 거래는 ★미청산★이다 — 남은 수량을 평가하지 않는다(시세가 없다). 그 거래에서 이미 판 몫의 실현 손익은 합계에 넣되 승률 통계에서는 빼고 따로 적는다.
- 매수 기록 없이 나온 매도(파일 시작 전에 산 것 · 공매도)는 손익을 계산할 수 없다 — 사유와 함께 따로 센다. v1 은 공매도를 다루지 않는다.
- 같은 시각의 체결은 파일에 나온 순서를 따른다.
- 당일 청산(진입일 = 청산일)과 하루 넘긴 거래를 가른다.

### 5.2 비용과 그 근거

| 성분 | 파일에 열이 있으면 | 없으면 |
|---|---|---|
| 수수료 | 그 값 — **관측** | 사용자가 넣은 요율 × 체결 대금 — **가정**(사용자 입력). 요율도 없으면 **미상** |
| 세금(매도) | 그 값 — **관측** | `market_rules.sell_tax_bp_on(체결일, 시장, 상품)` × 매도 대금 — **추론**(근거 등급과 출처를 함께). 시장·상품을 모르면 **미상** |

- 시장·상품은 체결 줄 → 종목 마스터(`stock_master.load_master_flags` — 있으면) → 사용자가 정한 "모르는 종목은 이렇게 본다"(**가정**) 순서로 정한다. 셋 다 없으면 미상이다.
  마스터에서는 ★실제로 아는 것만★ 읽는다 — 그룹 코드가 `ST` 일 때만 주식, `EF`(또는 ETF 표지)일 때만 ETF. 'ETF 아님'만으로 주식이라고 단정하지 않는다(ETN·ELW 일 수 있다).
- 비용은 ★맞춘 수량의 몫만큼★ 거래에 붙는다(체결 한 건이 두 거래에 걸치거나 일부만 맞춰질 때 — 수량 비례).
- 곡선·묶음의 손익 기준은 하나다: 모든 거래의 비용을 알면 '비용 뒤', 하나라도 모르면 ★섞지 않고★ '비용 앞'(응답의 `basis.pnl_basis`).
- ★미상은 0 이 아니다★ — 비용을 모르는 거래의 '비용 뒤 손익'은 `None` 이고, 합계에는 "비용을 모르는 거래 N건이 빠져 있다"고 적는다. 비용 앞 손익은 늘 계산된다.
- 유관기관 제비용 · 양도소득세 · 대주주 과세는 v1 에서 다루지 않는다(결과에 그렇게 적는다).

### 5.3 지표

거래(왕복) 단위, 비용 뒤 손익 기준(비용을 모르면 비용 앞 기준으로 따로):

- 거래 수 · 승 · 패 · 승률 · 평균 이익 · 평균 손실 · 손익비(평균 이익 ÷ 평균 손실) · 거래당 기대값 · Profit Factor(총이익 ÷ 총손실)
- 실현 손익 — 비용 앞 · 비용 뒤 · 비용 합계(수수료 · 세금) · ★비용 비중★(비용 ÷ 비용 앞 손익의 합 — 그 합이 0 이하이면 말하지 않고 사유를 적는다) · 거래 대금 대비 비용(bp — 늘 정의된다)
- ★손익분기 승률★ = (1 − 본전 거래의 비율) ÷ (1 + 손익비) — "지금 손익비라면 몇 할을 이겨야 본전인가"와 실제 승률의 차이.
  본전(손익 0) 거래의 몫을 빼는 까닭: 빼지 않으면 기대값이 0 인데 차이가 음수로 나온다 — ★차이의 부호가 기대값의 부호와 같아야 한다★(시험이 건다). 본전 거래가 없으면 1 ÷ (1 + 손익비) 와 같다.
- 최대 연속 손실(횟수 · 금액) — 본전 거래는 연속을 끊지 않는다(이익 거래가 끊는다) · 길이가 같으면 금액이 큰 쪽
- 가장 큰 손실 거래 · 가장 큰 이익 거래(각 다섯 건) — 거래 표가 앞 500건만 싣기 때문에 따로 둔다
- 누적 실현 손익 곡선(청산 시각 순)과 **고점 대비 하락(원)** · 그 최댓값. 고점은 출발선 0 에서 시작한다(첫 거래가 손실이면 그것이 곧 하락이다). ★%가 아니라 원이다★ — 계좌 평가금액을 모르므로 수익률·MDD(%)를 만들지 않는다.
- 보유 시간 분포(1분 미만 · 1~5분 · 5~30분 · 30분~당일 · 하루 넘김) — 구간마다 거래 수 · 승률 · 손익
- 진입 시간대별(시 단위) · 요일별 — 거래 수 · 승률 · 손익
- 종목별 — 거래 수 · 승률 · 손익 · 비용
- 날마다 — 거래 수와 그날 손익(거래를 많이 한 날이 더 벌었는가)
- **손실 직후의 진입** — 손실로 끝난 거래의 청산 뒤 10분 안에 시작한 거래와 그 밖의 거래를 갈라 거래 수 · 승률 · 기대값을 나란히(복수 매매의 흔적). 문턱(10분)은 응답에 적는다.

나눗셈의 분모가 0 이면 값은 `None` 이다(예: 손실 거래가 없을 때의 손익비). 표본이 작을 때의 경고: 거래가 30건 미만이면 "표본이 작다"고 적는다(통계를 숨기지는 않는다).

## 6. 라우트

`POST /api/v1/trade-journal/analyze` — `src/api/trade_journal_routes.py`

- 로그인 필요(`src/api/protected_routes.py` 에 등록 — 사유: 개인의 매매 기록을 다룬다).
- 요청: `{ fills: [...], commission_bp: number|null, unknown_market: "KOSPI"|"KOSDAQ"|null, unknown_instrument: "stock"|"etf"|null }`.
- 상한: 20,000줄. 넘으면 계산하지 않고 400 + 사유(잘라서 계산하지 않는다 — 앞부분만의 통계는 다른 통계다).
- ★저장하지 않는다★ — DB · 파일 · 로그에 체결 줄을 남기지 않는다(시험이 동작으로 건다: 계산 뒤 DB 쓰기 0 · 파일 쓰기 0). ★DB 감사 기록은 남기지 않는다★(설계 초안의 '감사 기록에 줄 수만'은 DB 쓰기 0 과 부딪혀 뺐다) — 앱 로그에 줄 수만 남긴다(종목·수량·금액 없음 · 시험이 건다).
- 응답: `inputs`(받은 줄 · 통과 · 버림) · `rejects`(앞 50건 + 사유별 개수) · `basis`(성분별 근거 — 관측·추론·가정·미상의 건수와 세율 출처) · `summary` · `curve` · `breakdowns` · `trades`(앞 500건) · `open_positions` · `unmatched_sells` · `not_covered`(다루지 않는 것의 목록).

## 7. 화면 (`/trade-journal`)

- 위젯 `frontend/src/widgets/trade-journal/` · 순수 로직(파일 읽기 · 열 어림 · 줄 정규화)은 `frontend/src/entities/trade-journal/` — 시험하기 쉽게 화면에서 뗀다.
- 세 단계가 한 화면에 위에서 아래로 쌓인다(마법사로 숨기지 않는다 — 돌아가서 열 대응을 고치는 일이 잦다).
  1. **파일** — 고르기(끌어 놓기 포함). "파일은 이 브라우저에서 읽고, 서버로는 맞춘 줄만 보냅니다. 서버는 저장하지 않습니다."
  2. **열 맞추기** — 필수 다섯 칸마다 파일의 열을 고른다 · 매수/매도 값 대응 · 앞 다섯 줄 미리 보기 · 수수료(파일의 열 / 요율 입력 / 모름) · 모르는 종목의 시장(추정하지 않음이 기본).
  3. **결과** — 요약 띠(거래 수 · 승률 · 손익비 · 기대값 · 손익분기 승률) → 누적 실현 손익과 고점 대비 하락(그림) → 비용 분해(막대 하나 — 비용 앞 이익에서 수수료·세금이 가져간 몫) → 보유 시간 · 시간대 · 요일(막대) → 종목 표 → 거래 표 → 버린 줄과 사유.
- 그림은 직접 SVG([ADR 004](../../decisions/adr-004-chart-library-boundary.md) · 표식 규격 `chartSpec`). 누적 곡선은 `shared/ui/perf/perfGeo.ts` 의 기하 도우미를 쓴다 — `PerfCurve` 를 그대로 쓰지 않는 까닭: 그 부품은 자산 곡선(처음을 1·100으로 · 낙폭 %)을 그리는데, 여기는 0 에서 시작하는 원 단위 손익과 원 단위 하락이다.
- 값마다 근거 표시: 비용이 추론·가정이면 그 칸에 "추론"·"가정" 표지와 출처 줄. 미상이면 `N/A` 와 사유(용어집 — 값 자리의 미상은 `N/A`).
- 문체: 개조식 + 합니다체 · 용어집(승률 · MDD 대신 여기서는 "고점 대비 하락") · 새 CSS 클래스만(`tj-*`) · 라이트·다크 AA.
- 내비게이션: '내 계좌' 앞에 "매매일지".

## 8. 시험

- 엔진: 손으로 계산한 작은 표본(시험에 싣는다)과 지표가 일치 · 짝(매수만 있는 파일 · 부분 체결 · 같은 시각 다건 · 비용 열 유무 · 미청산 · 매수 없는 매도) · 변이.

## 10. 주장의 범위

- 결과는 ★올린 파일 안에서 일어난 일★의 관측이다. 파일이 계좌의 전부인지, 빠진 체결이 없는지는 이 도구가 모른다.
- 세금의 추론은 보도 근거(T1)의 세율표로 한다 — 실제 정산과 다를 수 있다(파일에 세금 열이 있으면 그 값이 우선이다).
- 승률·기대값은 과거의 집계다. 앞으로의 성과를 말하지 않는다 · 예측력의 증거가 아니다.
